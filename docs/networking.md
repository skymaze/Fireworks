# 高速网络自动化说明

Fireworks 通过 WebUI 完成 DGX Spark 集群创建和成员扩容所需的高速网络探测、规划、配置与验证。正常流程不要求用户登录节点、编写 Netplan 脚本或手工执行 SSH 命令。

## 拓扑要求

每台节点使用以下四个固定 RoCE 接口；相同接口代表同一条 rail：

| rail | 接口 | 规划子网 |
|---|---|---|
| 0 | `enp1s0f0np0` | 第 1 个 `/24` |
| 1 | `enP2p1s0f0np0` | 第 2 个 `/24` |
| 2 | `enp1s0f1np1` | 第 3 个 `/24` |
| 3 | `enP2p1s0f1np1` | 第 4 个 `/24` |

所有节点的对应 rail 必须接入同一二层广播域，例如同一交换机上的同一 VLAN。节点原有 IP 网段可以不同：Fireworks 使用源地址 `0.0.0.0` 的 RFC 5227 ARP Probe 按 MAC 验证二层连通，不依赖双方已有地址处于同一三层子网。但修改 IP 无法跨越断线、错误接线、端口隔离或 VLAN 隔离，这些情况会在 WebUI 预检中直接指出节点与接口。

控制平面还需要节点管理网 SSH 可达、节点保存了可用的 sudo 密码，并且节点使用 Netplan/NetworkManager。管理接口不在高速网络接管范围内。

## 地址规划

集群 CIDR 至少为 `/22`，其中前四个 `/24` 依次分配给四条 rail。例如 `10.1.0.0/16` 使用 `10.1.0.0/24` 到 `10.1.3.0/24`。

成员使用持久化的 `net_index` 槽位。槽位 1 从 `.10` 开始，槽位 2 使用 `.11`，依此类推；`.1` 到 `.4` 留给 NVIDIA 官方工具。添加节点从当前最大槽位的下一个位置开始，并最多向后探测 16 个槽位以避开交换网络中已被其它设备占用的地址。删除最高槽位成员后再次添加可以自然复用该槽位；既有成员地址不会因扩容而变化。

CIDR 会在保存前规范化为网络地址。数据库中的其它集群网段和当前二层广播域中的实际 IP 占用都会参与判断，不能只依赖数据库记录。

## 创建集群流程

WebUI 选中节点后会先调用只读预检，提交创建时后端会再次执行同样的关键检查，降低预检与写入之间发生变化的风险。

1. 通过管理网 SSH 读取四个接口的存在性、carrier、operstate、MTU、MAC 和 IPv4 地址。
2. 分类现有配置：
   - `reuse`：所有节点已经使用相同规划、MTU 一致且槽位唯一，只验证不写 Netplan。
   - `reconfigure`：至少一个节点存在可识别规划，但节点间网段或 MTU 不一致；WebUI 推荐未被数据库与现网占用的新网段。
   - `configure`：未发现可完整复用的四 rail 规划，按表单规划新网络。
3. 检查四个接口 carrier，并以首台节点为锚点对其它节点执行每条 rail 的双向 ARP/MAC 探测。四台节点会完成 24 个方向性探测。
4. 对每个计划分配的 IP 执行本机绑定检查和主动 ARP 占用探测。发生冲突时返回具体节点、接口、IP、原因和应答 MAC，并继续寻找候选网段供 WebUI 自动更新。
5. 对需要重配的节点事务化应用 Netplan；任一节点失败便逆序回滚已修改节点。
6. 等待 NetworkManager 收敛，验证每台节点的四个本地规划 IP、RoCEv2 IPv4 GID，以及所有对应 rail 的跨节点连通性。
7. 网络全部通过后，才在一个数据库事务中创建集群、占用节点并保存成员槽位；最后建立成员间 SSH 互信。

## 添加节点流程

集群详情页的添加弹窗会自动执行预检：读取现有成员和候选节点快照、验证物理 rail、计算可用槽位，并主动探测四个目标 IP。

提交后后端持有集群级与节点级配置锁并重新预检，防止并发添加拿到同一槽位。候选节点若已精确匹配集群规划与槽位，只验证并复用；否则应用集群保存的规划。随后先验证新节点到全部成员的四 rail 连通，再逐个验证既有成员到新节点的反向连通。全部通过后才写入成员关系；失败会释放节点占用并回滚本次网络修改。

## Netplan 接管与回滚

Fireworks 的权威声明是 `/etc/netplan/999-fireworks-network.yaml`，其中只包含四个高速接口，不声明管理口或其它 NIC。

Netplan 会合并多个 YAML，`addresses` 等列表不能靠高优先级文件可靠清空。因此应用前会扫描既有 YAML，并同时识别接口键名、`match.name` 和 `set-name`。只有确实给目标高速口声明了地址或 DHCP 的条目才会被接管：原文件先保存为固定单名 `*.yaml.fw-bak`，再移除冲突接口条目，避免备份无限堆积。

每次写入依次执行 `netplan generate` 和 `netplan apply`。任一步失败会在节点内立即恢复本次写入前的文件并重新应用；后续连通或 GID 验证失败时，控制平面会删除 Fireworks 声明、还原接入前备份并应用 Netplan。删除集群时只有用户明确选择“清理网络”才执行同一清理动作；复用但未被 Fireworks 接管的现有配置不会被删除。

sudo 密码只通过 SSH stdin 发送，不会拼入远端命令行或进程参数。临时探测与应用脚本使用每次操作唯一的文件名，并在执行后清理。

## WebUI 错误与处理

| 错误码 | 含义 | 建议处理 |
|---|---|---|
| `network_physical_link_failed` | 接口缺失、无 carrier，或双向 ARP/MAC 探测失败 | 按提示检查具体接口、线缆、交换机端口和 VLAN |
| `network_ip_conflict` | 计划 IP 已绑定在其它接口或收到其它 MAC 的 ARP 应答 | 使用 WebUI 自动推荐的网段；若无推荐，释放现网地址后重试 |
| `network_reconfig_cidr_conflict` | 混合现网统一重配时选择了其中一个旧网段 | 接受 WebUI 填入的新空闲网段后重新提交 |
| `cidr_conflict` | 最终 CIDR 与数据库中的其它集群重叠 | 使用提示中的空闲网段 |
| `network_existing_verify_failed` | 可复用现网未通过本地 IP、GID 或跨节点验证 | 配置未被修改；先按详情修复对应 rail |
| `network_configure_failed` | SSH、sudo、Netplan generate/apply 或远端脚本失败 | 错误详情会包含失败阶段和回滚结果，修复节点环境后从 WebUI 重试 |
| `network_verify_failed_rollback` | 写入后本地地址、GID 或双向连通验证失败 | 本次修改已回滚；按结构化详情检查失败方向 |

## 真机验证基线

当前流程已在四台接入同一交换机、原有地址分别处于 `10.0.0.0/16` 与 `10.10.0.0/16` 的 DGX Spark 上完成 WebUI 端到端验证：预检识别混合网段并通过 24 个双向物理探测，确认 16 个计划 IP 可用后统一配置为 `10.1.0.0/16`、MTU 9000；随后从 WebUI 移除并重新添加第 4 台节点，复用槽位 4，最终高速网 ping 10/10 成功且无丢包。
