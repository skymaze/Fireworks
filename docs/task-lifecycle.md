# 任务发布、日志与数据生命周期

## 发布时的节点信息

配方中的节点级自动变量可能依赖 GPU、HCA、GID、网卡和磁盘信息。发布任务和生成
发布预览时，控制平面会并发调用所有已选节点的 Agent `/api/info`，成功后更新节点
快照，再进行配方渲染。任一节点不可达或信息读取失败时，本次操作直接失败，不会
回退使用添加节点时保存的旧参数。

集群的高速网地址仍以已经验证并提交的 `network_plan` 为准；节点刷新用于补齐当前
硬件能力，不会绕过集群网络规划。

## 容器日志

详情页通过一条 `docker logs -f --tail 1000` 流先回放最近日志，再无缝继续接收实时
日志，不再使用“HTTP 快照后再订阅”的双请求方式，因此两阶段之间没有丢行窗口。
控制平面为同一容器保留最多 1500 个日志段、合计最多 2 MiB 的回放缓存，后打开的
页面也能先看到近期历史。任务详情页重入时，即使浏览器复用了尚未退订的实时连接，
也会重置当前日志视图并回放离开期间的缓存；Agent 重连后会清空旧缓存并重新回放
最近 1000 行。

浏览器端日志缓冲最多保留约 2 MB，以避免长期运行页面无限占用内存。任务日志 API
仍可用于按 `tail` 数量读取容器快照。

## 停止 / 启动 / 重启

任务均为 docker compose 项目，生命周期操作**复用容器、不重建**：

- **停止**：`compose stop` 保留容器（GPU 释放）；停止后可「启动」复用
- **启动**（stopped/error）：`compose start` 复用容器；容器已被清理时自动回退 `compose up` 重建；无任何已记录容器时返回 409 提示重新发布
- **重启**（running）：`compose restart` 进程级重启（vLLM 重新加载模型）
- 启动/重启后自动补发健康检查；彻底释放磁盘请用「删除」（`compose down`）
- 健康检查以 **docker compose 声明的容器 healthcheck 为准**（配方可在 compose 声明
  Healthcheck）；配方未声明时降级为 head 的 vLLM `/v1/models` 探测（向后兼容）

## 删除任务

`Task` 是任务节点、推理统计样本和压测结果的聚合根。删除任务时，控制平面会在同一
事务内删除对应的 `TaskNode`、`InferenceSample` 和 `TaskBenchmark` 数据。任务表使用
SQLite `AUTOINCREMENT`，已删除的任务 ID 不会再次分配，避免异步结果关联到后创建的
任务。SQLite 的软引用由应用层维护；总览查询也只统计仍存在任务的压测记录。
